VULKAN SAILING GAME ENGINE - DETAILED IMPLEMENTATION ROADMAP
=============================================================

Purpose
-------
This document describes the systems, implementation order, validation steps,
and production tooling needed to build a C++20 Vulkan game engine for a sailing
game. It is written for the current project, which already uses CMake, Vulkan,
Vulkan-Hpp, GLFW, and GLM.

Technical assumptions:

1. Use C++20.
2. Support Windows first while keeping platform-specific code isolated.
3. Use Vulkan as the graphics API.
4. Use GLFW for window creation, Vulkan surfaces, and desktop input.
5. Use GLM for vector, matrix, and quaternion math.
6. Use CMake and Ninja for configuration and builds.
7. Run gameplay simulation at a fixed time step.
8. Keep rendering interpolation separate from authoritative simulation.
9. Start with a single-player architecture while keeping gameplay commands and
   state serializable for possible networking.
10. Use real-time approximations for ocean and fluid behavior instead of
    computational fluid dynamics.

PART 5 - SWAPCHAIN AND FRAME EXECUTION
=====================================

5.1 Swapchain
-------------
[ ] Query surface capabilities every time the swapchain is recreated.
[ ] Choose an sRGB surface format.
[ ] Prefer mailbox presentation when available for low-latency uncapped
    rendering.
[ ] Use FIFO as the guaranteed VSync mode.
[ ] Clamp the requested image count to surface limits.
[ ] Choose the swap extent from current framebuffer dimensions.
[ ] Select exclusive or concurrent sharing based on graphics/present queues.
[ ] Create one image view per swapchain image.
[ ] Create a depth image and view.
[ ] Select a supported depth format.
[ ] Add a stencil aspect only when the depth format contains stencil.
[ ] Recreate all size-dependent render targets after a resize.
[ ] Defer recreation while minimized.
[ ] Correctly handle VK_ERROR_OUT_OF_DATE_KHR.
[ ] Correctly handle VK_SUBOPTIMAL_KHR.
[ ] Destroy old swapchain resources only after the GPU no longer uses them.

5.2 Frames in flight

    [ ] In-flight fence or timeline value.
    [ ] Per-frame upload allocator.
    [ ] Per-frame descriptor allocator.
    [ ] Per-frame uniform data.
[ ] Wait only for the frame slot being reused.
[ ] Acquire the next swapchain image.
[ ] Reset frame-local resources.
[ ] Record commands.
[ ] Submit using synchronization2 where available.
[ ] Present.
[ ] Track which frame owns each swapchain image if fences are used.
[ ] Avoid vkDeviceWaitIdle during normal rendering.

5.3 Resource synchronization
----------------------------
[ ] Define which queue owns every resource.
[ ] Track image layouts.
[ ] Use precise pipeline stages and access masks.

    [ ] Upload completion before shader reads.

PART 8 - SHIP PHYSICS AND SAILING MODEL
=======================================

8.1 Rigid-body foundation
-------------------------
[ ] Decide whether to integrate a physics library or implement specialized ship
    dynamics.
[ ] A practical option is a general rigid-body library plus custom buoyancy and
    sail forces.
[ ] Represent vessel state:
    [ ] Position.
    [ ] Orientation quaternion.
    [ ] Linear velocity.
    [ ] Angular velocity.
    [ ] Mass.
    [ ] Center of mass.
    [ ] Inertia tensor.
    [ ] Accumulated force.
    [ ] Accumulated torque.
[ ] Use a fixed simulation step.
[ ] Use semi-implicit Euler or a more stable integrator.
[ ] Apply forces at positions to generate torque.
[ ] Transform between local and world space correctly.
[ ] Clamp or stabilize only when physically justified.

8.2 Buoyancy
------------
[ ] Approximate the submerged hull using:
    [ ] Multiple buoyancy sample points for the first version, or
    [ ] Submerged triangle integration for higher accuracy.
[ ] At each sample point:
    1. Query water height and normal.
    2. Calculate immersion depth.
    3. Apply upward buoyant force proportional to displaced volume.
    4. Apply water damping based on point velocity relative to water.
    5. Apply the force at the sample point.
[ ] Tune sample placement to represent bow, stern, port, and starboard volume.
[ ] Ensure the total buoyancy near equilibrium balances vessel weight.
[ ] Model center of buoyancy movement as the ship heels.
[ ] Test:
    [ ] Stable rest in flat water.
    [ ] Roll recovery.
    [ ] Pitch recovery.
    [ ] Response to a traveling wave.
    [ ] Added cargo mass.
    [ ] Off-center cargo.

8.3 Hydrodynamic resistance
---------------------------
[ ] Compute water-relative velocity.
[ ] Decompose velocity into hull-forward, sideways, and vertical components.
[ ] Apply low forward drag.
[ ] Apply strong lateral resistance to represent the keel.
[ ] Apply angular damping for roll, pitch, and yaw.
[ ] Increase drag with submerged area and speed squared.
[ ] Avoid arbitrary velocity assignment; use forces.
[ ] Add planing behavior only for hulls and speeds that require it.
[ ] Model grounding as contact forces plus hull damage.

8.4 Rudder and steering
-----------------------
[ ] Define rudder position and area.
[ ] Rotate rudder angle from helm input.
[ ] Calculate water flow at the rudder.
[ ] Produce lift roughly perpendicular to local flow.
[ ] Reduce authority at very low speed.
[ ] Allow reverse flow to reverse steering behavior where appropriate.
[ ] Apply force at the rudder location to generate yaw torque.
[ ] Clamp stall behavior at extreme rudder angles.
[ ] Add rudder response speed rather than instant angle changes.

[ ] Add gusts with smoothly varying noise.

4. Implement Renderer initialization in explicit stages.
   [ ] CreateInstance().
   [ ] SetupDebugMessenger().
   [ ] CreateSurface().
   [ ] SelectPhysicalDevice().
   [ ] CreateLogicalDevice().
   [ ] CreateAllocator().
   [ ] CreateSwapchain().
   [ ] CreateFrameResources().

5. Do not create important Vulkan data as temporary constructor variables.
   [ ] Store long-lived instance/device/swapchain resources as Renderer-owned
       members.
   [ ] Keep short-lived create-info structures local.

6. Replace raw public state with private members and narrow methods.
   [ ] Window exposes NativeHandle(), ShouldClose(), PollEvents(), and
       FramebufferSize().
   [ ] Renderer exposes Initialize(), DrawFrame(), OnResize(), and Shutdown()
       only if explicit shutdown is needed.

7. Enable validation and produce a clear screen.
   [ ] Stop and fix all validation errors before adding mesh rendering.

8. Add a fixed-step loop before implementing buoyancy.
   [ ] Keep render interpolation separate from authoritative physics.

9. Implement one feature at a time with an exit test.
   [ ] Never stack ocean, physics, assets, and gameplay on an unvalidated
       Vulkan foundation.
