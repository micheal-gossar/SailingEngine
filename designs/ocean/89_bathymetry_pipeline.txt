BATHYMETRY AUTHORING, COOKING, AND STREAMING CLASS DESIGN
=========================================================

Class
-----

    BathymetryPipeline

Purpose
-------

Create and stream one datum-correct, seam-free, uncertainty-aware seabed source
for coastal hydrodynamics, terrain rendering/collision, habitats, navigation,
acoustics, caustic receivers, and wetting/drying at every LOD.

Public API
----------

    Result<BathymetryDatasetId, BathymetryError> Cook(
        const BathymetryAuthoringManifest&);
    BathymetryRequest Request(
        BathymetryDatasetId, OceanCellKey, BathymetryLod, Priority);
    BathymetryStatus Poll(BathymetryRequest) const;
    BathymetrySnapshot Acquire(BathymetryRequest) const;
    BathymetrySample Sample(
        const BathymetrySnapshot&, const WorldPosition&) const;
    void Release(BathymetryRequest);

Key data structures
-------------------

BathymetryAuthoringManifest names source rasters/meshes/soundings, horizontal
CRS, vertical datum/geoid conversion, units, resolution, no-data policy,
shoreline/river/structure constraints, uncertainty, licenses/provenance, and
cook version. BathymetryTile stores signed seabed elevation zb in metres,
min/max elevation pyramids, gradients/curvature, bottom material/roughness/
porosity, uncertainty, wet-connectivity mask, canonical border samples, datum
and source hashes. SolverBathymetryPage adds cell areas, face depths/lengths,
restriction/prolongation operators, ghost rings, and terrain generation.

Algorithms and models
---------------------

Cooking reprojects sources into the world horizontal/vertical datum, rejects
unit ambiguity, merges by resolution/uncertainty/provenance, fills only bounded
no-data holes with a named method, and preserves larger unknown regions.
Hydrologic conditioning enforces authored sea connectivity, culverts/harbor
openings, river mouths, islands, and hard coastal structures without erasing
real shoals. A signed shoreline is extracted at the agreed datum and checked
against TerrainSystem collision/render meshes.

LOD generation is conservative and feature aware. Parent face/area values are
restricted from one canonical finest source; min/max pyramids retain hazards
and shoreline extrema. Solver restriction preserves water volume for a level
surface, while prolongation reconstructs bounded slopes without creating
negative depth. Neighbor borders are copied from a canonical edge owner,
including corners; mixed-LOD interfaces use precomputed flux-matching stencils.
Render meshes/height queries derive from the same tile version and use skirts
only for visual occlusion, never to change physical depth.

Flux stencils include face-area weights and fine/coarse temporal reflux layout;
they are generated from the same canonical geometry used by both tiles. Parent
and child face lengths, normals, datum samples, and connectivity sum/check
exactly within quantization tolerance. A tile package is invalid if a neighbor
can interpret its shared face with a different orientation or wet connection.

Runtime edits or destructible structures create a sparse delta generation.
Build a complete affected tile plus neighbor ghost/border generation, perform
conservative CoastalOceanSolver state remap, validate connectivity/volume, and
atomically switch. Streamed LOD selection includes a coastal solver safety ring
so a fine wet tile never abuts unavailable bathymetry.

Update rates, threading, and GPU ownership
-----------------------------------------

Cooking is offline. Runtime I/O/decompression/verification and delta rebuilds
run on jobs; activation occurs at an OceanDomain tick boundary. CPU double/
quantized source pages are authoritative. GPU height/minmax/material images are
read-only copies owned by TerrainSystem or the consuming renderer and carry the
same bathymetry generation. GPU filtering cannot feed solver or navigation.

Lifecycle and dependencies
--------------------------

Asset cooking validates datum and creates a manifest before packaging. At
runtime OceanStreamingService requests pages; BathymetryPipeline verifies and
publishes immutable snapshots; TerrainSystem and CoastalOceanSolver activate
matching generations in one dependency transaction. Readers pin pages through
generation swap. Shutdown cancels I/O and retires GPU copies through timelines.
See ..\world\26_terrain_system.txt, ..\world\10_world_streaming_manager.txt,
..\assets\44_asset_cooker.txt, 75_coastal_ocean_solver.txt,
83_underwater_habitat_renderer.txt, 85_ocean_streaming_persistence.txt, and
87_ocean_conventions_invariants.txt.

Failure and error behavior
--------------------------

Errors include UnknownDatum, UnitAmbiguity, ProjectionFailure, SourceConflict,
NoDataUnbounded, ShorelineMismatch, BorderMismatch, InvalidConnectivity,
UncertaintyExceeded, ChecksumFailure, GenerationMismatch,
ConservativeRemapFailure, and CapacityExceeded. Unknown depth is not zero and
cannot become navigable water. A failed delta leaves the prior full generation
active. Missing fine LOD may use a verified coarser solver page with explicit
error/confidence, but never an unrelated render mesh or interpolated land gap.

Deterministic and testing strategy
----------------------------------

Cook order, reprojection library/version, resampling kernels, edge owner, and
quantization are pinned in the manifest. Tests cover known datum offsets,
source overlap/uncertainty, no-data, signed islands/holes, narrow channels,
negative coordinates, parent/child volume restriction, min/max hazard retention,
same- and mixed-LOD edge identity, four-tile corners, gradient continuity,
terrain/collision/query alignment, tide wetting at shoreline, streamed
replacement, delta remap, save/replay hash, and thread-count-independent cook.

Performance and scalability
---------------------------

Use independently compressed pages, shared canonical borders, asynchronous
batched I/O, min/max-guided selection, memory-mapped cooked data where supported,
and separate source/solver/render representations. Budget source cache, solver
pages, upload bytes, and delta work. Track load/decode latency, cache hit,
border/LOD error, uncertainty coverage, pages pinned, remap time, and bytes.
Coarser fallback must remain within policy depth/gradient error near vessels.

Integration points and acceptance
---------------------------------

Terrain, coast, query, navigation, habitat, acoustics, media, and streaming all
name the same BathymetryGeneration. Stage acceptance requires zero same-LOD
border difference, mixed-LOD level-surface volume error below the configured
conservation tolerance, no lost min/max hazard, terrain/query elevation within
quantization tolerance, successful origin/stream churn, and an explicit failure
for unknown datum or unbounded no-data.

Engine-wide integration contract
--------------------------------

Normative offline dataset/runtime immutable page owner and world-streaming
participant. WorldStreamingManager owns leases/admission; AssetCooker owns the
offline transaction; Terrain/coast/navigation/habitat/acoustics retain the same
BathymetryGeneration snapshot. Unknown/no-data never becomes zero or navigable
water. CPU pages use root WorldPosition/SI/datum and GPU copies are
presentation-only generations retired through GpuCompletionSet. See
..\CANONICAL_CONVENTIONS.txt and ..\world\INDEX.txt.
