ENGINE INTEGRATION AND ACCEPTANCE MATRIX
========================================

Status and reading
------------------

Normative cross-system acceptance inventory. A row names the authoritative
owner, publication phase from FRAME_THREADING_MODEL.txt, consumer interface,
thread/lifetime, and required evidence. Unit/error rules come from
CANONICAL_CONVENTIONS.txt and ERROR_RESULT_POLICY.txt.

Ownership dependency DAG gates
------------------------------

Foundation:
    diagnostics/config/platform -> clock/jobs/VFS/schema -> registry/assets
World:
    coordinates/entities/commands -> physics/world streaming -> gameplay/ocean
GPU:
    runtime -> scheduler + memory -> frame retirement + resources/descriptors/
    swapchain -> render graph/providers -> renderer facade
Presentation:
    immutable world snapshots -> renderer/UI/audio; no reverse ownership

CI graph lint must distinguish:
    owns/constructs; calls synchronously; consumes snapshot; publishes event;
    registers participant; and offline tool dependency.
Only owns/constructs edges participate in lifetime-cycle detection. Snapshot
and event edges must name producer phase and generation. No ownership cycles
are allowed.

Integration gates
-----------------

Gate 0 - contracts:
    Unique canonical class/type names; Result policy; SI/axis/datum annotations;
    every cross-system datum has owner/phase/thread/lifetime; all references
    resolve; ownership DAG acyclic.

Gate 1 - foundation and assets:
    Stale handle/ID rejection; deterministic AssetId manifest; cooker byte
    determinism; bounded VFS parsing; dependency-cycle rejection; async cancel;
    hot reload last-known-good and generation retirement.

Gate 2 - Vulkan lifetime:
    Validation-clean bootstrap and 10,000-frame run on unified/split queues;
    no hidden barriers or normal-frame idle; per-queue monotonic timelines;
    release/resize/reload only after GpuCompletionSet; device-loss containment.

Gate 3 - fixed simulation:
    Render cadence/delta changes do not alter authoritative hashes. Command
    order, physics, sailing forces, weather/ocean seeds, events, and save replay
    remain stable across supported worker counts.

Gate 4 - world streaming:
    Multi-observer plan; activation rollback; terrain/collision/navigation/
    bathymetry generation alignment; pinned-reader eviction; negative/large
    cells; origin shifts with in-flight render frames; no blocking I/O.

Gate 5 - sailing and ocean:
    Buoyancy/hydrodynamics query only OceanQueryService generation N; exactly
    one force/reaction owner; N-to-N+1 wake coupling; CPU/GPU water conformance;
    coastal conservation and bounded visual residual. Ocean stage details are
    in ocean\90_ocean_staged_acceptance.txt.

Gate 6 - gameplay/save/network:
    Mission/economy transactions are acyclic and atomic; no recursive command
    dispatch; save captures immutable provider snapshots and restores all-or-
    nothing; persistent IDs resolve explicitly; malformed inputs are bounded;
    network transport absence does not affect single-player architecture.

Gate 7 - presentation:
    UI/HUD/accessibility and audio consume snapshots/events only; render delta
    affects presentation only; input focus/consumption is deterministic; audio
    callback allocation/lock tests pass; diagnostics/development UI cannot
    mutate state except through validated commands.

Gate 8 - lifecycle and faults:
    Partial construction and shutdown at every phase; worker/callback drain;
    save interruption; memory/descriptor/staging/pool pressure; missing/corrupt
    assets/cells; queue delay; resize/minimize; device loss; diagnostics failure;
    no leaks, use-after-free, silent fallback, or orphan registration.

Per-document implementability checklist
---------------------------------------

Every implementation issue linked to a design must answer:
1. Is the API normative or conceptual, and does a fallible call return Result?
2. Which service owns each mutable field and destruction?
3. Which phase/thread reads and writes it?
4. What are units, coordinate datum, TickId/generation, and seed stream?
5. What snapshot/lease keeps an asynchronous reader alive?
6. Which RenderGraph use and GpuCompletionSet protect GPU work?
7. What happens on stale input, capacity, cancellation, and shutdown?
8. Which test demonstrates no dependency cycle or reverse data flow?

Repository-level verification
-----------------------------

Run a design manifest check on every change: all .txt files listed once in
ARCHITECTURE_INDEX.txt; numbered design prefixes unique; relative .txt
references resolve; forbidden legacy dependency names do not reappear except in
explicit compatibility text. Implementation acceptance then combines targeted
unit tests, deterministic replay, Vulkan validation, sanitizers/static analysis,
fault injection, resource leak accounting, and platform performance envelopes.
