MISSION SYSTEM CLASS DESIGN
===========================

Class:

    MissionSystem

Purpose:

    Run data-defined mission graphs, objectives, conditions, rewards, and persistent progress without embedding UI logic.

Public API:

    Start(missionId);
    Abandon(instance);
    HandleEvent(GameEvent);
    Step();
    ActiveMissions();
    ObjectiveState(instance,node);
    Serialize()/Deserialize();
    ClaimRewards(instance);

Internal state and components:

    - mission definitions.
    - instance IDs.
    - node state graph.
    - event subscriptions.
    - condition evaluator.
    - pending reward transaction.
    - completion history.

Lifecycle and ownership:

    definitions immutable assets; system owns instances; subscriptions removed with instance; save stores IDs/state/version, not pointers

Error behavior:

    Invalid AssetId/graph/instance/event, capacity, stale transaction, and
    migration return MissionError. Completion remains PendingReward until one
    Inventory transaction result succeeds; failure rolls back no mission state
    and may retry idempotently.

Threading and timing constraints:

    simulation thread; events buffered and processed in sequence at tick boundary; completion/rewards committed atomically

Dependencies:

    - EntityRegistry.
    - Inventory transaction request/result interface.
    - AssetManager.
    - GameplayCommandBus.
    - SaveSystem consumes registered snapshots; no runtime ownership dependency.

Tests:

    - linear/branch mission.
    - simultaneous events.
    - invalid graph.
    - reward rollback.
    - save migration.
    - duplicate event idempotence.

Implementation rules:

    - Keep implementation-only types out of public headers.
    - Use RAII and generational IDs; do not expose owning raw pointers.
    - Validate descriptions before allocating or mutating state.
    - Publish complete snapshots/generations rather than partially updated data.
    - Add diagnostics for failure context without making logging a dependency
      of correctness.

Canonical integration contract:

    Normative MissionInstanceHandle owner. P8 consumes a stably ordered
    GameEvent batch and emits idempotent reward transaction requests keyed by
    mission/node/sequence. InventoryEconomySystem returns results but has no
    MissionSystem dependency, breaking the former cycle. UI receives mission
    snapshots only. Saves store AssetId, instance persistent ID, schema/version,
    node state, and pending transaction keys—not callbacks or EntityId.

    See 35_inventory_economy.txt, 59_gameplay_command_bus.txt, and INDEX.txt.
