PHYSICAL DEVICE SELECTOR CLASS DESIGN
=====================================

Class:

    PhysicalDeviceSelector

Purpose:

    Score Vulkan physical devices and produce a deterministic selection plus queue-family plan.

Public API:

    Select(instance,surface,requirements) -> Result<DeviceSelection,VulkanError>;
    EnumerateCandidates(...);
    ExplainRejection(device);
    BuildQueuePlan(candidate);

Internal state and components:

    - candidate properties/features/extensions/memory budgets/surface support.
    - queue-family assignments.
    - rejection records.
    - stable tie-break key.

Lifecycle and ownership:

    Selector owns no Vulkan handles. During bootstrap it returns a borrowed
    physical-device handle plus copied properties and queue plan; VulkanRuntime
    adopts the result only after selection succeeds.

Error behavior:

    Invalid requirements, query/backend failures, and no suitable device return
    VulkanError with deterministic per-candidate rejection records. Expected
    missing features are not exceptions.

Threading and timing constraints:

    Run during bootstrap on one thread; all queries complete before logical-device creation

Dependencies:

    - Vulkan bootstrap value types only; no VulkanRuntime dependency.
    - DebugDiagnostics.

Tests:

    - reject missing swapchain support.
    - prefer discrete within policy.
    - integrated fallback.
    - split graphics/present queues.
    - deterministic tie.
    - no suitable device.

Implementation rules:

    - Keep implementation-only types out of public headers.
    - Use RAII and generational IDs; do not expose owning raw pointers.
    - Validate descriptions before allocating or mutating state.
    - Publish complete snapshots/generations rather than partially updated data.
    - Add diagnostics for failure context without making logging a dependency
      of correctness.

Canonical integration contract:

    Normative stateless bootstrap policy. Candidate tie breaks use stable device
    identifiers/properties and configured policy, never enumeration order
    alone. QueuePlan identifies graphics/compute/transfer/present capabilities;
    CommandScheduler later creates per-queue timeline state.

    See 16_vulkan_runtime.txt, 19_command_scheduler.txt, and
    ..\ERROR_RESULT_POLICY.txt.
