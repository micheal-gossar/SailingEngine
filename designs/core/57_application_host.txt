APPLICATION HOST CLASS DESIGN
=============================

Class:

    ApplicationHost

Purpose:

    Construct services in dependency order and run the window/event, fixed simulation, and render loop with explicit shutdown.

Public API:

    ApplicationHost(AppOptions);
    Run()->ExitCode;
    RequestExit(reason);
    TickOnce(now);
    Suspend();
    Resume();

Internal state and components:

    - owned service graph.
    - Window/Runtime/Renderer/world.
    - SimulationClock.
    - exit state.
    - fatal error boundary.
    - frame statistics.

Lifecycle and ownership:

    unique_ptr services declared in reverse destruction order; constructor publishes only complete host; Run catches top-level recoverable/fatal errors

Error behavior:

    Constructor failure unwinds RAII before publication. Run is the top-level
    exception containment boundary and converts failures to contextual
    EngineError/ExitCode. Recoverable frame/tick Results are handled by their
    documented owner; fatal failure begins ordered shutdown once.

Threading and timing constraints:

    main thread owns loop/window/render submission; fixed-step loop bounded; jobs shut down after producers and before dependencies

Dependencies:

    - Composition root for all services; services never own ApplicationHost.
    - DebugDiagnostics.

Tests:

    - construction rollback.
    - fixed-step count.
    - minimized suspend.
    - orderly exit.
    - fatal exception logging.
    - device-lost policy.
    - destruction order.

Implementation rules:

    - Keep implementation-only types out of public headers.
    - Use RAII and generational IDs; do not expose owning raw pointers.
    - Validate descriptions before allocating or mutating state.
    - Publish complete snapshots/generations rather than partially updated data.
    - Add diagnostics for failure context without making logging a dependency
      of correctness.

Canonical integration contract:

    Normative composition and schedule owner. TickOnce executes P0-P16 in
    ..\FRAME_THREADING_MODEL.txt. Service fields are declared in construction
    order and destroyed in reverse following
    ..\OWNERSHIP_LIFETIME_SHUTDOWN.txt. Subsystems communicate through explicit
    references, snapshots, registrations, commands, and events; no service
    locator or owning cycle is allowed.
