ENGINE DESIGN ARCHITECTURE INDEX AND MANIFEST
=============================================

Status and scope
----------------

This is the canonical entry point for the programming-only architecture in this
directory. It describes code contracts, ownership, update order, and acceptance;
it does not specify game content or production art. The six root documents are
normative. Numbered class designs are implementable module contracts unless
explicitly labeled facade, optional, offline, or conceptual.

Canonical root documents
------------------------

    CANONICAL_CONVENTIONS.txt
        Names, IDs/handles, units, coordinates, time, Vulkan vocabulary, seeds.
    FRAME_THREADING_MODEL.txt
        P0-P16 update phases, logical threads, handoffs, and cycle breaks.
    OWNERSHIP_LIFETIME_SHUTDOWN.txt
        Sole owners, construction/destruction, borrowing, GPU retirement.
    ERROR_RESULT_POLICY.txt
        Result/Error rules, callbacks, transactions, and fallback behavior.
    INTEGRATION_ACCEPTANCE_MATRIX.txt
        Cross-system owner matrix and staged implementation gates.
    ARCHITECTURE_INDEX.txt
        This system map and complete document manifest.

Integrated system map
---------------------

    Platform events -> Input/UI -> GameplayCommandBus
                              |
    SimulationClock -> fixed P2-P12 coordinator
       |          |           |
       v          v           v
    world/time  EntityRegistry/PhysicsWorld <-> sailing force pipeline
       |          |                         uses OceanQuery generation N
       v          +--> gameplay/events/save snapshots
    WorldStreamingManager
       +--> terrain/navigation participants
       +--> OceanStreamingService --> OceanDomain publishes N+1
       +--> asset leases

    immutable render/audio/UI snapshots
                 |
       +---------+------------+
       v                      v
    Renderer                 UI/Audio
       |
    VulkanRuntime -> CommandScheduler timelines
       |             MemoryManager allocations
       +----------> GpuResourceManager records
                     |  RenderGraph synchronization
                     v
                 FrameManager retirement -> Swapchain present

Ownership arrows never point back from presentation to simulation. Apparent
reverse data flow uses a command/event queue, immutable generation, snapshot,
lease, or next-tick coupling record. See FRAME_THREADING_MODEL.txt.

Dependency-cycle decisions
--------------------------

* PhysicalDeviceSelector consumes bootstrap inputs; it does not own/depend on
  VulkanRuntime. WindowPlatform creates a surface for VulkanRuntime and has no
  reverse Vulkan dependency.
* CommandScheduler owns timeline values. FrameManager owns retirement and calls
  scheduler completion; scheduler does not depend on FrameManager.
  SwapchainManager/DescriptorAllocator receive frame/timeline values and do not
  depend on FrameManager. ShaderPipelineManager depends on descriptors, never
  the reverse.
* AssetCooker calls importer/processor interfaces; ModelImporter does not depend
  on the cooker. AssetManager consumes AssetRegistry snapshots; registry does
  not depend on manager. Runtime typed resources never become cooker owners.
* CollisionSystem owns shapes and PhysicsWorld consumes them; CollisionSystem
  has no runtime dependency on PhysicsWorld. WorldCoordinateSystem publishes
  rebase transactions; physics/terrain/camera register participants.
* VesselSystem is the sailing coordinator. Force subsystems consume a
  VesselStepContext and do not own/call VesselSystem. Ocean reactions cross the
  P9-to-next-P6 boundary.
* WorldStreamingManager owns the global residency plan. Terrain/navigation/
  ocean are participants. SaveSystem snapshots providers; streaming/gameplay
  do not depend on SaveSystem for their runtime behavior.
* InventoryEconomySystem owns atomic inventory transactions. MissionSystem may
  request one; inventory does not depend on missions. Network/UI/debug enqueue
  commands; GameplayCommandBus does not depend on those producers.
* DebugDiagnostics is foundational. Vulkan/frame/UI adapters publish snapshots
  to it; diagnostics does not own or depend on DevelopmentUI.

Bounded implementation choices
------------------------------

No cross-system ownership, phase, unit, lifetime, or failure-policy decision is
left unresolved. The following implementation choices remain intentionally
profiled/configurable and must satisfy the stated interfaces and acceptance:

* VMA versus a project allocator behind MemoryManager.
* Rigid-body backend and the exact supported deterministic CPU/build profile.
* Whether main, simulation, and render logical executors share OS threads on a
  platform; the P0-P16 order and snapshot handoffs do not change.
* Unified versus dedicated compute/transfer Vulkan queues selected from
  capabilities; the same RenderGraph DAG must work on either.
* Optional network transport/provider; NetworkReplicationModel remains
  transport-independent and single-player does not depend on it.
* Per-platform visual quality/performance thresholds and optional ocean models;
  authoritative minimums, seeds, units, query band, and save/network state do
  not change by visual tier.
